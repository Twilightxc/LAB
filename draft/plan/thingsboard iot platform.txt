### โมดูลที่ 1: บทบาทของ ThingsBoard ในฐานะ Headless Backend (BaaS)

**แนวคิดหลัก:**

* **Headless IoT BaaS:** ThingsBoard ทำหน้าที่เป็นแพลตฟอร์มจัดการอุปกรณ์ (IoT Device Management) และจัดการข้อมูลหลังบ้าน (Backend-as-a-Service) 
โดยไม่ต้องสร้าง Server, Database หรือ MQTT Broker ขึ้นมาเองตั้งแต่ศูนย์


* **Device Identity & Authentication:** อุปกรณ์ทุกตัวบนระบบจะถูกผูกเข้ากับ `Device Profile` และระบุตัวตนผ่าน **Device Access Token** 
เพื่อความปลอดภัยในการสื่อสารข้อมูล


* **Rule Engine Processing:** มีตัวประมวลผลกฎหลังบ้าน ทำหน้าที่กรองข้อมูล ตรวจสอบเงื่อนไขแจ้งเตือน (Alarm Rules) และกระจายข้อความแบบ Event-driven โดยอัตโนมัติ

> **สคริปต์คำพูดผู้สอน:**
> *"ในโลกการสร้างระบบ IoT ระดับอุตสาหกรรม เราไม่นิยมเขียนเซิร์ฟเวอร์รับ socket หรือตั้งฐานข้อมูล time-series เองทั้งหมด เพราะมีต้นทุนในการบำรุงรักษาสูง ThingsBoard 
เข้ามาทำหน้าที่เป็น BaaS หรือตัวจัดการหลังบ้านทั้งหมด ตั้งแต่รับการเชื่อมต่อจากอุปกรณ์ จัดเก็บประวัติข้อมูล ไปจนถึงส่งต่อไปยังแดชบอร์ด สิ่งที่เราต้องทำคือเข้าใจ 'ท่อส่งสัญญาณ' และ 
'รูปแบบข้อมูล' ให้ถูกต้องเท่านั้น"*

### โมดูลที่ 2: Data Modeling — Telemetry vs. Attributes

สิ่งที่วิศวกร IoT มักสับสนคือความต่างระหว่างข้อมูลสองประเภทนี้:

| มิติการเปรียบเทียบ | Time-series Telemetry | Attributes |
| --- | --- | --- |
| **ลักษณะข้อมูล** | ข้อมูลที่เปลี่ยนแปลงตามเวลาและมี timestamp กำกับ

 | ข้อมูลเชิงสถานะ หรือคุณสมบัติประจำตัวของอุปกรณ์ (Key-Value) |
| **การจัดเก็บ** | บันทึกลง Time-series Storage เก็บทุกค่าที่ส่งเข้ามา

 | เก็บเฉพาะ **'ค่าล่าสุดเพียงค่าเดียว'** (ทับค่าเดิมเสมอ) |
| **ตัวอย่างการใช้งาน** | อุณหภูมิ, การสั่นสะเทือน, ระดับพลังงาน

 | เฟิร์มแวร์เวอร์ชัน, หมายเลขซีเรียล, ค่าเกณฑ์แจ้งเตือน

 |
| **Topic MQTT ขาเข้า** | `v1/devices/me/telemetry` | `v1/devices/me/attributes` |

**Attribute Scopes (ขอบเขตของ Attributes):**

* **Client-side Attribute:** ข้อมูลที่ฮาร์ดแวร์รายงานขึ้นฝั่งเดียว (เช่น IP Address, MAC Address, เวอร์ชันเฟิร์มแวร์)


* **Shared Attribute:** ข้อมูลที่ควบคุมจากแดชบอร์ดเพื่อส่งต่อไปยังอุปกรณ์ (เช่น `samplingRate: 100`, สวิตช์ปิด/เปิดการทำงาน)
* **Server-side Attribute:** ข้อมูลคอนฟิกภายในที่อุปกรณ์มองไม่เห็น ใช้เฉพาะหลังบ้าน (เช่น `max_temperature_limit: 85.0`)

> **สคริปต์คำพูดผู้สอน:**
> *"อย่าส่งทุกอย่างเป็น Telemetry ถ้าเราส่งหมายเลขเครื่องหรือเฟิร์มแวร์เวอร์ชันเป็น Telemetry ทุก 1 วินาที ฐานข้อมูลจะบวมโดยเปล่าประโยชน์ 
ข้อมูลอะไรที่เปลี่ยนตามเวลาให้ใช้ Telemetry ข้อมูลอะไรที่เป็นสถานะคงที่หรือค่าตั้งค่า ให้ใช้ Attributes"*
>

### โมดูลที่ 3: สถาปัตยกรรมการสื่อสารสองทิศทาง (WebSocket & RPC)

**1. Multiplexed WebSocket API (`/api/ws/plugins/telemetry`):**

* ใช้ WebSocket ท่อเดียวเชื่อมโยงระหว่างเบราว์เซอร์กับเซิร์ฟเวอร์ เพื่อลดภาระ Connection Overhead
* หน้าเว็บส่งข้อความ **Subscription Command (`tsSubCmds`)** ระบุ Device ID และคีย์ที่ต้องการฟัง:
```json
{
  "tsSubCmds": [
    {
      "cmdId": 1,
      "entityType": "DEVICE",
      "entityId": "2a7b3c40-xxxx-xxxx-xxxx",
      "keys": "mock_val,system_status",
      "timeWindow": 60000
    }
  ]
}

```


* เมื่อ ESP32-S3 ยิงค่าใหม่เข้าสู่ ThingsBoard เซิร์ฟเวอร์จะกระจายข้อมูล (Push) เข้าท่อ WebSocket ของหน้าเว็บทันทีแบบ Real-time

**2. Two-Way Remote Procedure Call (RPC):**

* ใช้ควบคุมอุปกรณ์จากหน้าเว็บผ่าน HTTP POST ไปยัง:
`/api/plugins/telemetry/DEVICE/{deviceId}/rpc/oneway`
* ThingsBoard จะแปลงคำสั่งส่งต่อลงไปที่หัวข้อ MQTT `v1/devices/me/rpc/request/{requestId}` บนบอร์ด ESP32-S3


* ฝั่งหน้าเว็บต้องตั้ง Timeout ดักจับเสมอ เผื่อกรณีอุปกรณ์ออฟไลน์

### โมดูลที่ 4: การวางตัวเป็น Loop Engineer (Prompting & Verification)

**แนวคิด Loop Engineering:**

ไม่ใช่เพียงการให้ AI เขียนโค้ดให้เสร็จ แต่คือการทำหน้าที่เป็น **"สถาปนิกและผู้ตรวจสอบ (Auditor)"**

```
+--------------------+      Prompt with Spec      +--------------------+
|   Loop Engineer    | -------------------------> |      AI Agent      |
|  (User / Architect)| <------------------------- | (ChatGPT / Claude) |
+--------------------+        Raw JS Code         +--------------------+
          |
          v
[ Resilience & Security Audit ]
  1. มี Memory Leak (ล้าง Timer/Socket) หรือไม่?
  2. มี Reconnect Loop ถี่เกินไปจนเซิร์ฟเวอร์บล็อกหรือไม่?
  3. จัดการ Data Inconsistency (null, NaN) อย่างไร?

```

**3 กฎเหล็กในการตรวจสอบโค้ด AI ที่สร้างในคาบ:**

* **Resource Leak:** ตรวจดูว่าในโค้ดมีคำสั่งสั่งปิดการเชื่อมต่อ (`socket.close()`) หรือล้าง Timer (`clearTimeout`) ก่อนสร้างการเชื่อมต่อใหม่หรือไม่
* **Connection Flood:** หากเน็ตหลุด AI ส่วนใหญ่มักเขียนโค้ดยิง Reconnect รัว ๆ ในลูปทันที ซึ่งจะทำให้ติดบล็อก IP หรือเบราว์เซอร์ค้าง 
ต้องสั่งให้ใช้ **Exponential Backoff** (เพิ่มระยะเวลาหน่วงทวีคูณ เช่น 1s, 2s, 4s...)
* **Type Safety & Data Parsing:** โค้ดมีการใช้ `try...catch` ครอบ `JSON.parse()` หรือไม่ และมี fallback กรณีค่าที่อ่านได้เป็น `null` หรือไม่
